# Lab3 快递物流管理系统 - 领域模型总结

## 一、项目概述

### 系统目标
实现包裹全生命周期的跟踪管理，主要涵盖**揽收分拣**和**运输配送**两个核心业务环节。

### 核心能力
1. **包裹管理**：状态查询、历史轨迹追踪、当前位置获取
2. **车辆管理**：当前状态查询（位置、下一站、预计到达时间）
3. **中转站管理**：待处理和已处理包裹清单查询
4. **路径规划**：路径规划及变更历史记录

---

## 二、核心概念类（10个）

### 2.1 包裹相关（3个）

| 概念类 | 核心职责 | 关键属性 |
|--------|---------|---------|
| **运单** | 记录客户寄送包裹的信息 | 运单号、创建网点、目的网点 |
| **包裹** | 系统的核心业务对象，记录包裹全生命周期状态 | 包裹编号、当前状态、当前位置、下一站、预计到达时间 |
| **包裹轨迹** | 记录包裹位置和状态变化历史 | 轨迹编号、位置、状态、时间、操作类型 |

### 2.2 站点相关（2个）

| 概念类 | 核心职责 | 关键属性 |
|--------|---------|---------|
| **网点** | 客户寄送和接收包裹的服务站点 | 网点编号、网点名称、地址、类型 |
| **中转站** | 包裹运输过程中的中转节点 | 中转站编号、中转站名称、地址 |

### 2.3 运输相关（3个）

| 概念类 | 核心职责 | 关键属性 |
|--------|---------|---------|
| **车辆** | 运输包裹的交通工具 | 车辆编号、车牌号、容量、当前位置、下一站、预计到达时间、当前状态 |
| **司机** | 驾驶车辆运输包裹的人员 | 司机编号、姓名、联系方式 |
| **运输任务** | 系统为包裹分配的运输工作 | 任务编号、起点、终点、状态、实际出发时间、实际到达时间 |

### 2.4 路径规划相关（2个）

| 概念类 | 核心职责 | 关键属性 |
|--------|---------|---------|
| **路径规划** | 为包裹规划的运输路径 | 规划编号、起点、终点、规划路径、预计总时间、是否当前有效 |
| **路径规划历史** | 记录路径规划变更历史 | 历史记录编号、变更原因、变更时间、变更位置 |

### 2.5 分拣相关（1个）

| 概念类 | 核心职责 | 关键属性 |
|--------|---------|---------|
| **分拣任务** | 在网点或中转站对包裹进行分拣的工作任务 | 任务编号、分拣地点、创建时间、完成时间、状态 |

## 三、核心关系（15个）

### 3.1 包裹相关关系（6个）

1. **运单 → 包裹**（1:1 组合）
   - 一个运单对应一个包裹，包裹不能脱离运单存在

2. **包裹 → 包裹轨迹**（1:N 组合）
   - 一个包裹有多条轨迹记录，记录完整历史

3. **包裹 → 路径规划**（N:1 关联）
   - 一个包裹有多个路径规划，但只有一个当前有效

4. **包裹 → 路径规划历史**（1:N 关联）
   - 一个包裹可能有多次路径规划变更

5. **包裹 ↔ 运输任务**（N:M 关联）
   - 一个包裹可能经过多个运输任务，一个运输任务可以包含多个包裹

6. **包裹 ↔ 分拣任务**（N:M 关联）
   - 一个包裹可能经过多次分拣，一个分拣任务可以包含多个包裹

### 3.2 站点相关关系（3个）

1. **网点 → 运单**（1:N 关联）
   - 一个网点可以创建多个运单，也可以接收多个运单

2. **网点 → 分拣任务**（1:N 关联）
   - 一个网点可以执行多个分拣任务

3. **中转站 → 分拣任务**（1:N 关联）
   - 一个中转站可以执行多个分拣任务

### 3.3 运输相关关系（3个）

1. **司机 → 车辆**（1:N 关联）
   - 一个司机可以驾驶多辆车

2. **车辆 → 运输任务**（1:N 关联）
   - 一辆车可以执行多个运输任务

3. **运输任务 → 路径规划**（N:1 关联）
   - 多个运输任务依据同一个路径规划生成

### 3.4 路径规划相关关系（2个）

1. **路径规划历史 → 路径规划**（原规划，N:1 关联）
   - 记录原路径规划

2. **路径规划历史 → 路径规划**（新规划，N:1 关联）
   - 记录新路径规划

### 3.5 其他关系（1个）

1. **分拣任务 → 网点/中转站**（N:1 关联）
   - 分拣任务在网点或中转站执行

## 四、关键业务规则

### 4.1 包裹状态流转规则
```
已揽收 → 分拣中 → 待运输 → 运输中 → 已到达
                              ↓
                            异常
```

### 4.2 路径规划规则
- 包裹在起点会规划好全程路线
- 路径规划可以变更，但需要记录变更历史
- 路径变更通常发生在中转站
- 一个包裹只有一个当前有效的路径规划（isCurrent=true）

### 4.3 分拣规则
- 根据路径规划中的下一站进行分拣
- 分拣异常需要标记包裹为异常状态

### 4.4 运输任务分配规则
- 根据车辆容量、路线规划、当前位置等因素分配
- 车辆状态必须为"空闲"或"运输中"才能接受新任务

### 4.5 轨迹记录规则
- 包裹的每个状态变化都必须记录轨迹
- 轨迹记录按时间顺序排列，形成完整的历史轨迹链

## 五、模型验证场景

### 场景一：查询包裹当前状态 ✅
**需求**：客户输入运单号，系统显示包裹当前状态、当前位置、下一站、预计到达时间

**模型支持**：
- 包裹实体直接包含所需属性
- 查询路径：运单号 → 包裹 → 直接获取状态信息

### 场景二：记录调度历史记录和变更原因 ✅
**需求**：记录路径规划变更历史，包括变更原因、历史路线规划详情、预计到达时间

**模型支持**：
- 路径规划历史实体专门设计用于记录变更历史
- 查询路径：包裹 → 路径规划历史 → 原路径规划/新路径规划

### 场景三：车辆当前状态和装载清单 ✅
**需求**：查询车辆当前状态，以及车辆在某个中转站应该装载的包裹清单

**模型支持**：
- 车辆实体直接包含状态信息
- 查询路径：车辆 → 运输任务（起点=中转站）→ 包裹

## 七、模型设计特点

### 7.1 完整性
- 覆盖包裹全生命周期的所有关键环节
- 支持正常流程和异常流程
- 支持路径规划变更等扩展需求

### 7.2 可追溯性
- 包裹轨迹记录完整的历史状态变化
- 路径规划历史记录完整的变更过程
- 所有关键操作都有时间戳记录

### 7.3 查询便利性
- 关键查询信息直接存储在实体属性中
- 关联关系设计合理，支持多维度查询
- 无需复杂的计算和聚合即可满足基本查询需求

### 7.4 扩展性
- 实体设计留有扩展空间
- 支持未来可能的新需求
- 关系设计灵活，便于添加新的关联

## 八、设计原则

1. **业务驱动**：以业务需求为核心，设计符合业务逻辑的模型
2. **职责清晰**：每个概念类职责明确，避免职责重叠

4. **易于维护**：模型结构清晰，便于理解和维护
5. **中文命名**：所有概念和属性都使用中文命名

## 十、快速参考

### 核心查询路径

1. **查询包裹状态**：运单号 → 包裹
2. **查询包裹轨迹**：包裹编号 → 包裹轨迹（按时间排序）
3. **查询路径规划历史**：包裹编号 → 路径规划历史 → 原路径规划/新路径规划
4. **查询车辆状态**：车辆编号 → 车辆
5. **查询车辆装载清单**：车辆编号 → 运输任务（起点=中转站）→ 包裹
6. **查询中转站待处理包裹**：中转站编号 → 分拣任务（状态=待处理）→ 包裹

### 关键枚举类型

- **PackageStatus**：已揽收、分拣中、待运输、运输中、已到达、异常
- **VehicleStatus**：空闲、运输中、维护中、已停用
- **TaskStatus**：待分配、已分配、运输中、已完成、已取消
- **SortingTaskStatus**：待处理、处理中、已完成、异常
- **OperationType**：揽收、分拣、装车、卸车、到达、异常

## 总结

本领域模型完整地支持了快递物流管理系统的核心业务需求，通过10个核心概念类和15个关键关系，实现了包裹全生命周期的跟踪管理。模型设计遵循业务驱动、职责清晰、关系合理的原则，具有良好的完整性、可追溯性、查询便利性和扩展性。
