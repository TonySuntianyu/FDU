# 领域模型验证分析

## 1. 验证概述

本文档通过选取关键业务场景，验证领域模型对系统目标的支持程度。系统的主要目标是实现包裹全生命周期的跟踪管理，并提供包裹、车辆、中转站的基本查询能力。

## 2. 验证场景

### 场景一：查询包裹当前状态（当前位置、下一站）

**需求描述**：
客户输入运单号，系统显示包裹当前状态"运输中"，历史轨迹"揽收→分拣→中转"，当前位置"上海分拣中心"，下一站"杨浦中转站"，预计到达时间"2025-12-01 10:00"

**模型支持分析**：

1. **查询包裹基本信息**：
   - 通过运单号（waybillNumber）查询包裹（Package）实体
   - 包裹实体包含：
     - `currentStatus`：可直接获取当前状态"运输中"
     - `currentLocation`：可直接获取当前位置"上海分拣中心"
     - `nextStation`：可直接获取下一站"杨浦中转站"
     - `estimatedArrivalTime`：可直接获取预计到达时间"2025-12-01 10:00"

2. **查询历史轨迹**：
   - 通过包裹编号关联查询包裹轨迹（PackageTrack）实体集合
   - 按时间戳（timestamp）排序，获取历史轨迹序列
   - 轨迹记录包含：
     - `location`：位置信息
     - `status`：状态信息
     - `operationType`：操作类型（揽收、分拣、中转等）
   - 可以组合成"揽收→分拣→中转"的轨迹描述

**结论**：✅ **模型完全支持**
- 包裹实体的属性设计直接支持当前状态、位置、下一站、预计到达时间的查询
- 包裹轨迹实体支持历史轨迹的完整记录和查询
- 无需额外的复杂查询逻辑，直接通过实体属性即可满足需求

---

### 场景二：记录调度的历史记录和变更原因

**需求描述**：
包裹在到达中转站时，由于天气变化需要调整后续路线。系统需要记录路线变更的历史，包括变更原因，能够查询历史路线规划详情和预计到达时间。

**模型支持分析**：

1. **路径规划变更记录**：
   - 路径规划历史（RoutePlanHistory）实体专门用于记录路径变更
   - 包含关键属性：
     - `originalPlan`：关联原路径规划（RoutePlan）
     - `newPlan`：关联新路径规划（RoutePlan）
     - `changeReason`：记录变更原因（如"天气变化"）
     - `changeTime`：记录变更时间
     - `changeLocation`：记录变更发生的位置（中转站）

2. **路径规划详情查询**：
   - 原路径规划（RoutePlan）包含：
     - `plannedRoute`：规划的路径（站点序列）
     - `estimatedTotalTime`：预计总运输时间
     - `createTime`：规划创建时间
   - 新路径规划（RoutePlan）同样包含完整信息
   - 通过路径规划历史可以追溯完整的变更过程

3. **包裹关联查询**：
   - 路径规划历史（RoutePlanHistory）关联包裹（Package）
   - 可以查询某个包裹的所有路径规划变更历史
   - 当前有效的路径规划通过`isCurrent`标志标识

**业务流程支持**：
1. 包裹到达中转站时，系统检测到需要变更路线
2. 创建新的路径规划（RoutePlan），设置`isCurrent=true`
3. 将原路径规划的`isCurrent`设置为`false`
4. 创建路径规划历史记录（RoutePlanHistory），记录：
   - 原路径规划和新路径规划
   - 变更原因（天气变化）
   - 变更时间和位置
5. 更新包裹的路径规划关联

**结论**：✅ **模型完全支持**
- 路径规划历史实体专门设计用于记录变更历史
- 支持完整的变更原因、时间、位置记录
- 通过关联关系可以追溯完整的路径规划详情
- 支持查询历史路线规划和预计到达时间

### 场景三：车辆当前状态和在某一个中转站应该装载的包裹清单

**需求描述**：
系统需要能够查询车辆当前的状态（当前位置、下一站、预计到达时间），以及车辆在某个中转站应该装载的包裹清单。

**模型支持分析**：

1. **车辆当前状态查询**：
   - 车辆（Vehicle）实体包含：
     - `currentLocation`：车辆当前位置
     - `nextStation`：车辆下一站
     - `estimatedArrivalTime`：预计到达下一站的时间
     - `currentStatus`：车辆当前状态（空闲、运输中、维护中等）
   - 直接通过车辆实体即可获取所有当前状态信息

2. **车辆关联的运输任务**：
   - 车辆（Vehicle）关联多个运输任务（TransportTask）
   - 运输任务包含：
     - `origin`：起点位置
     - `destination`：终点位置
     - `status`：任务状态（待分配、运输中、已完成）

3. **中转站待装载包裹查询**：
   - 查询逻辑：
     a. 根据中转站位置，查询所有分拣任务（SortingTask）
     b. 筛选状态为"已完成"的分拣任务
     c. 获取这些分拣任务关联的包裹（Package）
     d. 筛选包裹的下一站（nextStation）与车辆下一站匹配的包裹
     e. 同时筛选包裹的当前状态为"待运输"或"已分拣"
   
   - 或者通过运输任务查询：
     a. 查询起点为指定中转站的运输任务（TransportTask）
     b. 筛选状态为"待分配"或"运输中"的运输任务
     c. 获取这些运输任务关联的包裹
     d. 如果运输任务已分配给车辆，则这些包裹属于该车辆

4. **车辆装载清单生成**：
   - 对于指定车辆和指定中转站：
     a. 查询车辆当前关联的运输任务（TransportTask）
     b. 筛选起点为指定中转站的运输任务
     c. 获取这些运输任务关联的所有包裹（Package）
     d. 这些包裹即为该车辆在该中转站应该装载的包裹清单

**数据关联路径**：
```
车辆(Vehicle) 
  → 运输任务(TransportTask) [起点=中转站]
    → 包裹(Package)
```

**结论**：✅ **模型完全支持**
- 车辆实体直接支持当前状态查询
- 通过车辆-运输任务-包裹的关联关系，可以查询车辆应该装载的包裹
- 通过分拣任务-包裹的关联关系，也可以查询中转站待处理的包裹
- 模型设计支持灵活的查询需求

## 3. 扩展场景验证

### 场景四：包裹分拣异常处理

**需求描述**：
分拣过程中发现包裹地址不清晰、标签损坏或目的地不明确的情况，需要重新核对包裹信息或联系发件人确认地址。包裹需要标记为异常状态，等待处理。

**模型支持分析**：

1. **异常状态标记**：
   - 包裹（Package）实体包含：
     - `isAbnormal`：布尔值，标识是否处于异常状态
     - `abnormalReason`：异常原因描述（如"地址不清晰"、"标签损坏"、"目的地不明确"）

2. **分拣任务异常处理**：
   - 分拣任务（SortingTask）包含：
     - `status`：任务状态，可以设置为"异常"
   - 当发现异常时：
     a. 更新分拣任务状态为"异常"
     b. 更新包裹的`isAbnormal=true`
     c. 记录`abnormalReason`
     d. 创建包裹轨迹记录，记录异常状态

3. **异常处理流程**：
   - 系统可以查询所有`isAbnormal=true`的包裹
   - 根据异常原因进行分类处理
   - 处理完成后，更新`isAbnormal=false`，继续正常流程

**结论**：✅ **模型完全支持**
- 包裹实体直接支持异常状态和异常原因的记录
- 分拣任务状态支持异常标记
- 可以完整记录异常处理流程

---

## 4. 模型优势总结

1. **完整性**：
   - 覆盖了包裹全生命周期的所有关键环节
   - 支持正常流程和异常流程
   - 支持路径规划变更等扩展需求

2. **可追溯性**：
   - 包裹轨迹记录完整的历史状态变化
   - 路径规划历史记录完整的变更过程
   - 所有关键操作都有时间戳记录

3. **查询便利性**：
   - 关键查询信息直接存储在实体属性中
   - 关联关系设计合理，支持多维度查询
   - 无需复杂的计算和聚合即可满足基本查询需求

4. **扩展性**：
   - 实体设计留有扩展空间
   - 支持未来可能的新需求（如车辆维护、司机排班等）

## 5. 模型改进建议

1. **性能优化考虑**：
   - 对于高频查询的包裹状态信息，可以考虑冗余存储
   - 对于历史轨迹查询，可以考虑分表存储

2. **数据一致性**：
   - 包裹的`currentStatus`、`currentLocation`、`nextStation`需要与最新的轨迹记录保持一致
   - 建议通过领域服务或应用服务来维护这些一致性

3. **业务规则封装**：
   - 路径规划变更的业务规则可以封装在路径规划服务中
   - 包裹状态流转规则可以封装在包裹服务中
